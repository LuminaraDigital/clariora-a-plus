# APX + AI Coach: 10x Production Plan

Status: implemented (Phases 0-3), production rollout gated on the steps in section 0. Owner: CEO gate (see "Loop engineering"). Date: 2026-10-03.

## 0. Implementation status and deviations

What shipped, and where the build differs from the plan text below. The plan text is kept as written so the reasoning stays reviewable.

- **Phase 0:** done. Hint Pack eliminates a distractor in practice (hidden in mock and diagnostic modes), Mock Unlock starts a full mock, Pro Pass grants Pro per activated day, AI Burst reads multi-device ledgers, spends use the local balance only, and AI budget windows are per tier and per pass. Tests: `tools/test_store_fulfilment.js`, `tools/test_entitlements.js`, `tools/test_rate_limit_defense.js`.
- **1.1 Reservation size:** the 700-token target ignored the server-side prompt (system prompt, memory pack, similar items). The honest figure for a Pro explain is about 1,800 tokens, down from 3,800 (2.1x more burst headroom, not 5.4x). Multi-turn requests now bill every turn, which they did not before.
- **1.2/1.3 Cache key:** keyed on the canonical question material (`qid`, stem, sorted options, correct and chosen answer text, objective, distractor notes, specialist, model) rather than `choiceIndex`, because the client shuffles options. Cacheable requests drop every client field that is not in the key (free-form prompt, domain, history, turn count), so one client cannot plant text in a reply served to others. `tools/test_coach_cost_guards.js` asserts that equal keys mean byte-identical model input.
- **1.3 Read and write rules:** any eligible explain request may be served a cached row, including from learners with memory (rows are impersonal, so they only lose personalisation). Only requests with no memory boot pack write rows, and only when the reply came from the requested provider and passed every guard. Tool lists are fixed server-side for cacheable requests. Every exit after a reservation settles it exactly once, including thrown errors and abandoned streams (`tools/test_coach_handler_settlement.js`).
- **1.3 Rollout:** `AI_EXPLAIN_CACHE` is opt-in: `"1"` on staging, `"0"` on production until the soak in `docs/APX_ECONOMY_OPS.md` passes.
- **1.4 Pre-warm:** `tools/prewarm_explain_cache.js` is built and smoke-tested but has not been run, because it spends about 2.7M provider tokens. About 3,100 pairs over 1,032 standard questions.
- **1.5/1.6:** refine turns drop the memory pack and similar items. `GET /api/v1/admin/ai-cost?days=7` reports spend by provider, model and intent, cache hit rate and per-user outliers. Prices in `workers/ai_pricing.js` are estimates until `AI_PRICE_JSON` is set from invoices.
- **2.1/2.2:** answer-consistency guard (kill switch `AI_GUARD_CONSISTENCY="0"`, which also disables caching) and objective citation check. Retired 1101/1102 citations are redirected to the current 1201/1202 exam.
- **2.3:** similar items carry real stems from `workers/bank_stems.js`, a Worker-only module generated by `tools/build_similar_neighbors.py`. Stems are premium content: they are never shipped in `dist_web` and are stripped from tool results returned to clients. No correct answers are included.
- **2.4:** `tools/eval_coach.js --ci` runs in CI over `tools/fixtures/coach_golden.json` (10 labelled cases, not 100; grow it from real misses). `--live` mode exists for staging.
- **3.1/3.2:** `GET /api/v1/admin/apx-anomalies?days=7` reports over-budget user-days, test-grant sources, and the holdout readout (1,377 users per arm for a 5-point D7 lift; "inconclusive" until reached). Telemetry now records the holdout arm.
- **3.3:** waits for two weeks of telemetry, as planned.
- **Security fixes found on the way:** secret-leak patterns kept regex state between replies (some leaks passed on alternate calls); AWS, GitHub and private-key patterns added; injection detection now scans the question as well as the prompt; client-supplied `_similarItems` can no longer reach the trusted tool block.
- **Not built:** `STORE_FULFILMENT_V2` is client code with no runtime flag; rollback is revert and redeploy.

## 1. What "10x" means here

"10x better" is only useful if it is measured. The plan targets these numbers, each with a baseline taken from the code or the simulator today:

| Metric | Today | Target | How it is measured |
|---|---|---|---|
| Paid store items that deliver nothing | 2 (Hint Pack, Mock Unlock) | 0 | `tools/test_store_fulfilment.js` (new) |
| Paid AI passes that can deliver zero AI | 24-hour pass, if bought after heavy free use in the same month | 0 | `tools/test_token_budget_windows.js` (new) |
| Spend allowed above the local ledger balance | Yes (peer-device bonus) | No | `tools/test_ledger_unlocks.js` |
| Budget reserved per "explain" request on Pro | 3,800 tokens | 700 tokens (5.4x more burst headroom) | unit test on `estimateReservation` |
| AI cost per explanation | 1 model call per request | 2.5x cheaper at 60% cache hit rate, 5x at 80% | `ai_usage_log` + cache hit counters |
| AI replies that contradict the bank's correct answer | Not detected | 0 shown to learners (rejected and replaced by the bank explanation) | guard counter + eval harness |
| Explanation quality for free users | 8B model, live | 70B-quality, pre-generated and validated | eval harness score |
| APX effect on retention | Unknown | Measured go/no-go | 10% holdout, D7 retention |

The cache and pre-warm numbers come from the bank size: about 1,270 questions in `shards/`, so there are about 3,810 (question, wrong choice) pairs. That key space is finite and small, which is why caching pays off so strongly here. Pre-generating all of them costs about 2.7M tokens once.

## 2. Phase 0: fix what is broken in production (P0, ship first)

These are defects in live code. Nothing else ships until they are green.

### 0.1 Make Hint Pack deliver

- Where: `ledger_ui.js` (OWNED_ACTIONS ~667-688), `js/engine.js` (question render), `js/entitlements.js`.
- Behaviour: during practice (not full mocks or timed exams), a "Use hint" button appears when `hasActiveUnlock('HINT_PACK')` is true. Using it calls `consumeUnlock('HINT_PACK', qid, ...)` and auto-eliminates one wrong option using the existing `toggleEliminateOption`, plus shows the objective reference. One charge per question, idempotent on `qid`.
- Remove the "consume from the store panel" action; charges are spent only where the value is delivered.
- Acceptance: buying gives 10 charges, each use removes exactly one distractor and one charge, and the button is hidden in exam mode.

### 0.2 Make Mock Unlock deliver

- Where: `js/entitlements.js` `startExamFactory` (~1141). Before `openUpgrade('full_mock')`, check `hasActiveUnlock('MOCK_UNLOCK')`. If true, `consumeUnlock('MOCK_UNLOCK', sessionId, ...)` and start the exam.
- Delete the dead `apx_mock_session_unlock` flag write in `ledger_ui.js:685`.
- Consume on start, not on purchase. If the exam crashes before question 1, the charge is restored (consume on first answered question if a start-then-crash refund is simpler to prove).
- Acceptance: a free user with one charge can start one full mock, and the second attempt shows the upgrade sheet.
- Existing buyers: their charges already sit on the ledger, so both fixes make past purchases usable with no refund script.

### 0.3 Stop peer-device overspend

- Where: `ledger_engine.js` `getState` (~1000) and `spendUnlock` (~1605).
- Change: expose `wallet.balance` as the local chain balance (spendable) and `wallet.totalAcrossDevices` for display. `spendUnlock` checks the local balance only. `replayWallet` asserts the balance never goes below 0 after a spend block.
- UI copy: "Spendable on this device: X APX (Y across all devices)".
- Acceptance: a test with a peer device holding 5,000 APX and a local balance of 100 cannot buy a 450 item.

### 0.4 Fix AI budget windows

- Where: `workers/token_budget.js` (reserve ~166-197, settle ~325-341), `workers/api_entitlement_store.js`.
- Change: replace the per-user calendar-month key with a budget-window key:
  - free and pro_monthly and lifetime: `YYYY-MM:<tier>`
  - daily_pass: `pass:<tier_started_at>`, so each 24-hour pass gets its own fresh 25,000 tokens, scoped to that pass and not the calendar day.
- Store it in the existing `ai_tokens_month` column (TEXT). No migration is needed, and old values simply fail to match and reset, which is safe.
- Acceptance tests: (a) a free user at 30,000 tokens this month buys a pass and gets the full 25,000. (b) Two passes in one month each get 25,000. (c) A pass bought at 23:00 UTC cannot exceed 25,000 across the midnight boundary.

### 0.5 Small correctness fixes

- `ledger_engine.js:972` wallet cache uses `Array.isArray` on an object, so the cache never hits. Change it to `typeof === "object"`.
- `tools/test_apx_mastery_suite.js`: the "unlock fulfilment" check must assert a delivered effect (an option was eliminated, an exam started), not just that `consumeUnlock` was called. This is why 0.1 and 0.2 slipped through.

**Phase 0 gate:** `npm test`, `python tools/apx_economy_sim.py --ci --n 200` green, new tests green, staging deploy and manual buy-use smoke test of both items, then production deploy.

## 3. Phase 1: AI cost efficiency

### 1.1 Right-size reservations

- Where: `workers/coach_handler.js` `estimateReservation` (~504).
- Change: per-turn completion = the provider's `max_tokens` from `workers/api_ai_providers.js` (350 or 450), not a flat 700. Turns = 1 for `explain` (the orchestrator already stops after turn 1 for explain, `coach_orchestrator.js:622`), 2 for non-war-room intents, and tier `maxTurns` only for `war_room`.
- Keep the pessimistic floor of 512. `settleBudget` still reconciles to real usage.
- Acceptance: a Pro explain request reserves at most 700 tokens for a 1,000-character prompt.

### 1.2 Send the question ID

- Where: `js/tma_ghost_coach.js` (~101-154).
- Add `qid`, `choiceIndex`, `bankVersion` to the coach payload. This unlocks caching (1.3) and the Vectorize similar-item path, which currently gets no ID.

### 1.3 Explanation cache in D1

- New table (migration `0004_ai_explain_cache.sql`, mirrored in `workers/schema.sql`):
  `ai_explain_cache(cache_key TEXT PRIMARY KEY, qid TEXT, choice_index INTEGER, prompt_version TEXT, model_class TEXT, body TEXT, validated INTEGER, hits INTEGER, created_at INTEGER)`.
- Key = SHA-256 of `qid | choiceIndex | intent | promptVersion | modelClass | bankVersion`.
- Only cache `intent = explain` requests with no personal context (no `_memoryBlock`, no miss history), so no learner data ever lands in a shared row.
- Only store replies that passed the guards in Phase 2.
- Billing decision: a cache hit costs 0 tokens but still counts toward the daily call allowance, so the free-tier call cap stays a working upgrade lever.
- Invalidation: bumping `promptVersion` or `bankVersion` makes old rows miss. A weekly cron deletes rows older than 90 days.
- Acceptance: the second identical request returns from cache, logs `cache_hit=1`, and does not change the token counters.

### 1.4 Pre-warm with a stronger model

- New: `tools/prewarm_explain_cache.js`. It iterates the ~3,810 (question, wrong choice) pairs, calls the 70B model on staging, runs the Phase 2 guards, and writes validated rows.
- One-off cost is about 2.7M tokens. Run it on staging first, sample 50 outputs for human review, then copy the rows to production.
- Effect: free users receive 70B-quality explanations at zero marginal cost.

### 1.5 Cheaper refinement turns

- Where: `workers/coach_orchestrator.js` (~583).
- On turn 2 and later, drop the memory block and similar-item list from the resent prompt, and keep only the question, official answer, and previous draft.
- Measure the per-turn token drop in `ai_usage_log` before and after.

### 1.6 Cost visibility

- New `workers/ai_pricing.js`: price per 1M input/output tokens per provider and model.
- Add `cache_hit`, `intent`, `prompt_tokens`, `completion_tokens` columns to `ai_usage_log`.
- New authenticated admin endpoint `GET /api/v1/admin/ai-cost?days=7` returning cost by day, tier, provider, and cost per active learner.

**Phase 1 gate:** unit tests for reservation sizing and cache keys, a staging soak (100 scripted explain calls, cache hit rate reported), the dashboard returns sane numbers, then production behind flag `AI_EXPLAIN_CACHE=1` (default off, then on).

## 4. Phase 2: less hallucination (grounding)

This is the answer to "does the AI use the backend to hallucinate less". Testnet is not involved. Grounding comes from the question bank and objectives, which the backend already holds.

### 2.1 Answer-consistency guard (largest win)

- Where: `workers/coach_security_guard.js` next to `validateModelOutput` (~195).
- The request already carries the bank's correct answer. Reject any reply that names a different option as correct, or says the official answer is wrong. On rejection, return the bank explanation plus distractor analysis (`generateLocalRemediation`) and increment `guard_contradiction`.

### 2.2 Objective citation check

- The system prompt requires an objective ID (for example "1.3"). The guard checks it against the `OBJECTIVES` map in `coach_orchestrator.js`. Unknown IDs are stripped and counted. A missing citation is allowed but counted.

### 2.3 Real similar-item context

- `coach_handler.js:279-295` sends similar item IDs with empty stems. Fill the stems and correct answers from the bank shard, so "compare with question X" is grounded and not invented.

### 2.4 Eval harness

- New `tools/eval_coach.js` plus `tools/fixtures/coach_golden.json` (100 hand-checked misses across all domains).
- CI mode (no network): replays recorded model outputs through the guards and asserts that contradiction, unknown-objective, and leak counts are zero for the accepted set.
- Live mode (manual, staging): calls each provider and reports pass rates per model. It runs before any model or prompt version change.

**Phase 2 gate:** the eval passes in CI, the live eval on staging shows 0 accepted contradictions, and guard counters appear in the cost dashboard.

## 5. Phase 3: APX integrity and proof of value

### 3.1 Server-side anomaly flags (observe, never punish)

- Using the existing `apx_events` and `apx_daily_counters`: a nightly query flags accounts whose budgeted daily mint exceeds 160 or whose non-budgeted mints (for example `TEST_GRANT`) appear in production.
- Output is a count in the admin endpoint. Accounts are not modified. Flags become the eligibility filter if a leaderboard ever ships (server-validated points only, as the earlier plan requires).

### 3.2 Holdout readout

- The 10% holdout (`js/apx_holdout.js`) answers whether APX improves retention. With a 30% D7 baseline, detecting a 5-point lift at 80% power needs about 1,378 users per arm. With a 10% holdout that is about 13,800 total users. A 3-point lift needs about 37,600.
- Until those numbers are reached, report the result as "inconclusive" rather than reading early noise. If the user base is too small, raise the holdout to 50% for a fixed four-week window and accept the temporary loss of APX for half the learners.

### 3.3 Economy simulator update

- Add the Hint Pack and Mock Unlock real consumption rates to `tools/apx_economy_params.json` once Phase 0 telemetry has two weeks of data. The sim's unspent-balance band (200-1200) then validates sinks against real behaviour, not assumptions.

**Phase 3 gate:** the anomaly query runs on staging data, the holdout report prints sample sizes and confidence intervals, and the sim stays green.

## 6. Rollout, rollback, and release discipline

- Order: staging Worker (`clariora-a-plus-staging`), smoke, then production (`clariora.com.au`), using `python tools/build_web_dist.py` then `python tools/deploy_cloudflare.py`.
- Migrations: apply to `clariora_edge_db_staging` first, then `clariora_edge_db`. All new tables are additive, and the migration file includes `IF NOT EXISTS`.
- Feature flags: `AI_EXPLAIN_CACHE`, `AI_GUARD_CONSISTENCY`, `STORE_FULFILMENT_V2`. Each can be turned off without a redeploy.
- Rollback: previous Worker version ID recorded per deploy. Revert with `wrangler rollback <id>`. Client changes are revert-and-redeploy.
- Desktop: sync touched files into `CompTIA_A_Plus_Desktop_App/resources/app/` in the same change.
- CI (`.github/workflows/ci.yml`): add the new tests and `node tools/eval_coach.js --ci`.

## 7. Loop engineering (how the work is run)

Each task runs through the same loop: build, self-check, independent review, then a CEO gate.

| Role | Owns |
|---|---|
| CEO | Scope, phase gates, go/no-go on production deploys, final double check |
| Economy specialist | Phase 0.1-0.3, 3.x, simulator bands |
| Backend / Workers specialist | Phase 0.4, 1.1, 1.3, 1.6, migrations, deploys |
| AI/ML specialist | Phase 1.4-1.5, 2.x, eval harness |
| Frontend specialist | Hint and Mock UI, coach payload, copy, desktop sync |
| Verifier | Runs every gate and reproduces each acceptance test independently. Has no authority to edit, only to block. |

Per-task check: the owner runs the task's acceptance test. The verifier re-runs it from a clean checkout and runs `npm test` plus the sim.

Per-phase check: the full suite, a staging deploy, the smoke test, and the CEO sign-off recorded in the phase PR description.

Final check: the verifier re-runs every acceptance test in this document against production, confirms each metric in section 1 against its target, and opens a fix task for anything that misses. The plan is done only when that list is empty.

## 8. Out of scope

- Testnet (TON testnet, XDC Apothem, Stars sandbox). It is only for payment rails and has no effect on APX or AI grounding. See `docs/APX_ECONOMY_OPS.md`.
- Making APX tradeable, transferable, or cash-convertible.
- New AI providers or models. Phase 2's eval harness must exist before any are added.
